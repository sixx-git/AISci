# 方向一：Closing the Loop — 论文大纲与实验设计方案

> **建议标题**：*Closing the Loop: A Bidirectional Framework for AI-Driven Scientific Discovery with Quality-Aware Iterative Refinement*
>
> **中文标题**：《闭环式 AI 科研助手：基于质量感知迭代优化的双向框架》

---

## 一、核心思想与卖点

现有 AI for Science 工作（AI-Scientist、MOOSE、DeepMind ALE Theia 等）集中在**生成侧**：自动读文献、提假设、做实验、写论文。但一个根本问题被忽视了：**生成的内容质量如何评估？谁来告诉 AI "这个假设设计有漏洞"、"实验对比不充分"？**

你的工作填补了这块空白：

- **App A（评分表生成器）** = 质量评估引擎：自动从源文献提取知识结构，生成领域专属高质量评分表，对科研报告进行多维度质量诊断
- **App B（假设生成器）** = 内容生成引擎：理解科学问题，整合文献与数据证据，生成候选假设并转化为研究计划
- **闭环结合** = App B 生成的研究报告/实验计划，交由 App A 进行质量评分；评分结果反馈给 App B 驱动迭代优化，形成 "生成-评估-改进" 的科研闭环

**核心卖点**：不是做另一个 AI-Scientist，而是做 **AI-Scientist 的 "质量守门人"**，并证明 "评估反馈能显著提升生成质量"。

## 二、论文大纲

### Abstract（250词）

**结构**：
1. **背景与问题**：LLM 在科研内容生成（假设提出、实验设计）方面进展迅速，但缺乏自动化质量评估机制，导致生成内容可能存在逻辑漏洞、证据不足、方法论缺陷等问题
2. **方法**：提出双向闭环框架，将质量感知评分表自动生成系统与科研内容生成系统耦合。前者从源文献提取知识结构并生成三维质量评估标准（信息获取/科学推理/报告综合），后者基于文献与数据生成候选假设及研究计划
3. **关键机制**：质量评分结果通过结构化反馈通道回传至生成端，驱动针对性的迭代优化（如补充对比实验、强化理论论证、修正方法论缺陷）
4. **实验结果**：在 claim verification、data analysis、literature review 三类科研任务上，闭环迭代版本相比单次生成在评分表总分上平均提升 XX%，Critical 项通过率提升 XX%
5. **贡献**：首次将 "生成-评估-迭代" 闭环引入 AI 辅助科研，证明质量感知反馈对科研内容生成的显著改进作用

### 1. Introduction

**1.1 背景：AI 辅助科研的浪潮**
- AI-Scientist (2024)：端到端自动论文生成
- MOOSE / ALE Theia：假设提出与实验发现
- AI-Researcher：文献综述到发表全流程
- 共同特点：侧重 "生成"，评估环节薄弱（多为人工检查或简单指标）

**1.2 问题：生成质量缺乏自动化评估**
- LLM 生成内容可能存在 "幻觉"、逻辑跳跃、证据选择性呈现
- 人工评审耗时长，难以规模化
- 现有自动评估（如 RAGAS、G-Eval）多为通用指标，缺乏**领域适配性**和**科研-specific 维度**

**1.3 观察：评分表是科研评估的通用语言**
- 同行评审、课程作业、项目验收都使用评分表
- 高质量评分表需要领域知识 + 结构化思维，恰好是 LLM 的强项
- 但手动编制评分表耗时、主观、难以跨领域复用

**1.4 本文贡献**
- **C1**：提出首个面向科研内容生成的质量感知闭环框架，将自适应评分表生成与假设生成系统耦合
- **C2**：设计三维度评分体系（IA/SR/Synth）与角色分级机制（Critical/Mandatory/Standard），实现细粒度质量诊断
- **C3**：提出概念泛化与术语过滤的级联机制，解决跨领域评分表迁移时的术语泄露问题
- **C4**：在三种科研任务类型上验证闭环迭代相比单次生成的显著提升

### 2. Related Work

**2.1 AI 辅助科研内容生成**
- AI-Scientist：Sakana AI，端到端论文生成
- MOOSE：ICLR 2025，LLM 自主假设发现
- ALE Theia：DeepMind，假设→实验→模式发现
- AI-Researcher：文献到发表全流程
- **对比**：这些工作都没有将 "质量评估反馈" 纳入生成循环

**2.2 自动化评估与评分**
- RAGAS：RAG 系统评估框架
- G-Eval：LLM-as-judge 评估
- 传统自动评分系统（ETS e-rater等）：基于规则/ML，缺乏领域适应性
- **对比**：这些评估框架是 "静态打分"，不与生成系统形成闭环

**2.3 评分表自动生成**
- 现有工作多为教育领域的简单模板填充
- 缺乏针对科研报告的多维度、领域自适应生成方法
- **定位**：本文首次将评分表生成提升到科研质量保障层面

**2.4 LLM 迭代优化与自我修正**
- Self-Refine、Reflexion：LLM 自我修正
- **对比**：本文的迭代是由**结构化质量评估**驱动的，而非 LLM 自省，反馈更精准、可解释

#### 3.2 App A：质量感知评分表生成系统

**3.2.1 三维度评分体系**
- **Information Acquisition (IA, 20%)**：评估报告对源文献信息的提取与组织能力
  - 定义准确性、分类完整性、对比清晰度、数据引用准确率
- **Scientific Reasoning (SR, 65%)**：评估科学推理深度
  - 机制分析、方法对比、瓶颈识别、策略论证、量化分析
  - 使用 Bloom 认知层级动词（analyze, derive, argue, quantify, trace）
- **Report Synthesis (Synth, 15%)**：评估报告综合与呈现质量
  - 结构逻辑、论证连贯性、结论支撑度

**3.2.2 角色分级与权重机制**
- **Critical (4分, ~15-30%)**：核心质量门槛，不通过则报告存在根本性缺陷
- **Mandatory (2分, ~40-55%)**：重要质量指标，反映报告主体质量
- **Standard (1分, ~25-35%)**：基础规范检查
- **动态调节**：根据源文档数量自动调整角色分布，确保评分表适配不同复杂度任务

**3.2.3 概念泛化与术语过滤**
- **概念泛化层**：LLM 将源文档特有术语抽象为领域通用概念
  - 例："FedAvg" → "the baseline aggregation algorithm"
- **术语过滤层**：二次 LLM 调用区分 "领域通用术语" 与 "论文特有术语"
- **效果**：跨领域迁移时术语泄露从 20+ 处降至 0-1 处

**3.2.4 防答案泄露机制**
- 检测评分项中是否包含结论性表述（"proven that"、"refutes the claim"）
- 确保评分项考核的是 "分析过程" 而非 "是否知道答案"

#### 3.3 App B：科研内容生成系统

**3.3.1 系统架构**
- **输入**：科学问题 + 相关文献集合
- **处理**：
  1. 文献结构化解析（提取方法、数据、结论、局限性）
  2. 证据整合（跨文献对比、矛盾识别、证据链构建）
  3. 候选假设生成（基于证据 gap 提出可验证假设）
  4. 研究计划转化（假设 → 实验设计/分析任务/文献调研方向）
- **输出**：结构化研究报告 / 实验计划 / 文献综述

**3.3.2 与 App A 的接口**
- 接收 App A 生成的 task.json（评分表）
- 根据评分项反向指导生成策略（如：Synth 要求 "对比实验" → 在计划中强制加入对照组设计）

#### 3.4 闭环迭代机制

**3.4.1 反馈通道设计**
- **维度级反馈**：IA/SR/Synth 各维度得分率，识别薄弱环节
- **角色级反馈**：Critical/Mandatory/Standard 通过率，定位核心缺陷
- **项级反馈**：具体未通过的评分项文本，提供精准改进方向

**3.4.2 迭代策略**
- **策略 1：缺陷驱动补充**（Missing Evidence）
  - 若 SR "对比实验" 项未通过 → 补充对照实验设计
- **策略 2：深度强化**（Insufficient Depth）
  - 若 IA "机制定义" 项未通过 → 深化概念解释，补充形式化定义
- **策略 3：结构重组**（Poor Synthesis）
  - 若 Synth "论证连贯性" 项未通过 → 重构报告逻辑框架

**3.4.3 终止条件**
- 硬终止：达到最大迭代次数（默认 3 轮）
- 软终止：总分提升率 < 5% 或连续两轮无 Critical 项新增通过

### 4. Experimental Design

#### 4.1 研究问题

- **RQ1**：评分表生成质量如何？与人工编制的评分表相比，覆盖度、区分度、跨领域泛化性如何？
- **RQ2**：闭环迭代是否能显著提升生成报告的质量？相比单次生成，提升幅度如何？
- **RQ3**：不同迭代策略（缺陷驱动/深度强化/结构重组）对不同类型科研任务的改进效果有何差异？
- **RQ4**：评分表的角色分级机制（Critical/Mandatory/Standard）是否能有效识别报告的根本性缺陷？

#### 4.2 数据集

**基准数据集构建**：

| 任务类型 | 数据集 | 规模 | 来源 |
|---------|-------|------|------|
| Claim Verification | SciFact + 自建（FL/PEFT 领域论文） | 30 组 | 已有测试数据 test1/test2 |
| Data Analysis | 自建（FL 训练日志 + PEFT 性能数据） | 25 组 | 已有测试数据 test1/test2 |
| Literature Review | 自建（PEFT/联邦学习/医疗 AI 综述） | 25 组 | 已有测试数据 test1/test2 |

**每组成分**：
- 研究问题（query）
- 源文献（3-10 篇论文或数据文件）
- 人工编写的 "黄金标准" 报告（由领域专家撰写）
- 人工编制的评分表（与黄金标准报告配套）

#### 4.3 Baseline 方法

| 方法 | 描述 | 目的 |
|------|------|------|
| **Single-Shot** | App B 单次生成，不经过评估反馈 | 验证闭环价值 |
| **Self-Refine** | App B 生成 → LLM 自我评审 → 自我改进 | 对比 "无结构化评估" 的迭代 |
| **Human-Rubric** | 使用人工编制评分表进行评估 | 验证自动生成评分表的质量 |
| **Static-Template** | 使用固定模板评分表（不根据源文献自适应） | 验证自适应生成的必要性 |
| **Ours (Closed-Loop)** | 完整框架：生成 → 评估 → 迭代（最多 3 轮） | 本文方法 |

#### 4.4 评估指标

**4.4.1 评分表质量指标**
- **Coverage**：评分项覆盖黄金标准评分表的比例
- **Specificity**：评分项的平均 specificity 评分（1-5，由专家判断）
- **Cross-Domain Transfer**：跨领域迁移时的术语泄露数量
- **Source Coverage**：评分项引用源文献的比例（IA/SR 要求 100%）

**4.4.2 生成报告质量指标**
- **Rubric Score**：在人工评分表上的总分（百分比）
- **Critical Pass Rate**：Critical 项通过率
- **Improvement Delta**：迭代前后分数差
- **Human Evaluation**：专家盲评（1-5 分，维度：科学性/完整性/逻辑性/创新性）

**4.4.3 效率指标**
- **Time Cost**：单次生成 vs 单次闭环迭代的时间开销
- **Token Cost**：API 调用 token 消耗
- **Convergence Round**：达到收敛所需的迭代轮数

#### 4.5 实验流程

**Experiment 1：评分表生成质量评估**
- 对 3 种任务类型 × 2 个测试领域（FL、PEFT）运行 App A
- 对比输出与人工样例的：项数分布、角色分布、source_ids 覆盖率、术语泄露数
- 邀请 2-3 名领域专家进行盲评

**Experiment 2：闭环迭代效果验证**
- 对每组数据运行：Single-Shot → Self-Refine → Ours (Closed-Loop)
- 记录每轮迭代的评分变化
- 分析不同任务类型下的收敛速度

**Experiment 3：消融实验**
- 去掉概念泛化：术语泄露对生成质量的影响
- 去掉角色分级：所有评分项权重相同的效果
- 去掉特定维度（如去掉 Synth）：对整体评分的影响

**Experiment 4：跨领域泛化性**
- 在训练时未见过的领域（如医疗 AI、气候模型）上测试
- 验证评分表生成和闭环迭代的领域迁移能力

### 5. Discussion

**5.1 闭环框架的边界**
- 在什么类型的科研任务上效果最显著？（推测：structured tasks > open-ended exploration）
- 迭代次数的上限与边际效益递减

**5.2 评分表质量对闭环效果的影响**
- 如果评分表本身有偏差（如过度关注某类方法），迭代会放大偏差吗？
- 如何设计 "元评估" 机制来校准评分表

**5.3 与人工评审的对比**
- 自动评分 vs 专家评分的相关性分析
- 自动系统的优势（一致性、可规模化）与局限（创造性判断、领域直觉）

**5.4 伦理与未来方向**
- 自动化科研评估的责任归属
- 向 "完全自主科研" 演进的路径：当前框架是 "人在回路"（human-in-the-loop），未来可探索 "AI 自主迭代"

---

### 6. Conclusion

- 总结核心贡献：首次提出 "生成-评估-迭代" 闭环框架，证明质量感知反馈对科研内容生成的显著改进作用
- 强调方法论创新：三维度评分体系、角色分级、概念泛化、防答案泄露
- 展望未来：将框架扩展至更多科研领域（生物医学、材料科学、社会科学），探索 "评估即服务"（Evaluation-as-a-Service）的开放科学基础设施

### 3.2 需要补充的工作量

   - 跨文献对比（方法 A vs 方法 B 的性能对比表）
   - 矛盾识别（文献1声称 X，文献2声称 not X）
   - 证据链构建（支持/反对某一假设的文献集合）

3. **候选假设生成**
   - 基于 "证据 gap" 提出假设："现有方法在 Y 场景下表现差，可能是因为 Z"
   - 假设可验证性检查（是否可设计实验验证）

4. **研究计划转化**
   - 将假设转化为具体任务：
     - 实验设计 → 对照组、指标、数据集
     - 数据分析 → 分析维度、可视化方案、统计检验
     - 文献调研 → 检索关键词、筛选标准、综合框架

**产出**：可独立运行的 App B CLI 工具，支持三种任务类型的内容生成

#### 阶段二：闭环接口与迭代机制（1-2 周）

1. **反馈通道设计**
   - 解析 App A 的评分结果（task.json + rubric_scores.json）
   - 生成结构化反馈 prompt（"你在 X 方面得分低，需要补充 Y"）

2. **迭代策略实现**
   - 三种策略的 prompt 模板：缺陷驱动 / 深度强化 / 结构重组
   - 策略选择逻辑（基于未通过评分项的类型自动选择）

3. **终止条件判断**
   - 分数提升率计算
   - 连续轮次无改进检测

**产出**：闭环 orchestrator 脚本，串联 App A + App B

#### 阶段三：实验与评估（2-3 周）

1. **黄金标准报告编写**
   - 对现有测试数据（test1/test2 的三种任务），人工撰写 "理想报告"
   - 邀请领域专家（或自己）编写配套评分表
   - 工作量：约 10-15 份报告，每份 2000-5000 字

2. **Baseline 实现**
   - Single-Shot：App B 直接生成
   - Self-Refine：LLM 自我评审（Reflexion 风格）
   - Static-Template：固定模板评分表

3. **实验运行与数据分析**
   - 运行所有 baseline + 本文方法
   - 收集评分数据、收敛曲线、时间开销
   - 绘制对比图表

4. **人工评估**
   - 邀请 2-3 名同学/老师进行盲评（如果时间/人脉允许）
   - 或采用 "自我盲评"（间隔一周后再评）

#### 阶段四：论文撰写（2-3 周）

1. **初稿撰写**：按大纲完成各章节
2. **Related Work 完善**：补充最新文献（2024-2025）
3. **图表制作**：系统架构图、实验结果图
4. **反复修改**：根据导师/合作者反馈迭代

### 3.3 总工作量估算

| 阶段 | 时间 | 核心任务 | 风险点 |
|------|------|---------|--------|
| App B 完善 | 2-3 周 | 实现文献解析、假设生成、计划转化 | App B 的生成质量不稳定，需要大量 prompt 调优 |
| 闭环接口 | 1-2 周 | 反馈通道、迭代策略、终止条件 | 反馈 prompt 设计是关键，可能需要多轮测试 |
| 实验评估 | 2-3 周 | 黄金标准报告、baseline、数据分析 | 黄金标准报告编写耗时；人工评估资源 |
| 论文撰写 | 2-3 周 | 初稿、修改、图表 | 写作周期容易被拖延 |
| **总计** | **7-11 周** | | |

### 3.4 工作量是否足够？

**结论：工作量充足，甚至可以支撑一篇高质量的会议/期刊论文。**

理由：
1. **技术深度足够**：App A 已有成熟的三代系统，技术细节丰富（概念泛化、术语过滤、角色分级、防泄露）
2. **创新点明确**："生成-评估-闭环" 是现有 AI for Science 工作的明确补充，定位清晰
3. **实验可验证**：三种任务类型 × 多领域 × 多 baseline 的实验设计，结果可信度高
4. **可扩展性强**：即使时间有限，也可以：
   - 先完成一个任务类型（如 claim verification）的完整闭环验证
   - 其他两个任务类型作为 "泛化性验证" 简要呈现

### 3.5 降低风险的建议

1. **MVP 策略**：先聚焦 claim verification 类型，完成 "App B 生成 → App A 评估 → 迭代改进" 的最小闭环，验证核心假设后再扩展
2. **App B 复用**：App B 不需要从零开发，可以基于现有 LLM + RAG 框架（如 LangChain/LlamaIndex）快速搭建原型
3. **黄金标准替代**：如果编写完整报告耗时，可以先用 "专家修改版"（对 App B 单次输出进行人工精修）作为黄金标准
4. **评估自动化**：用 App A 的评分结果作为主要指标，减少人工评估依赖
